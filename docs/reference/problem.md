# 문제 정의

## 상황

온라인 할인 행사가 정해진 시각에 시작합니다.
시작 직후 1분 동안 회원이 한꺼번에 몰려서 한정 수량 쿠폰을 받고, 할인된 상품을 주문합니다.
이때 쿠폰과 재고는 정해진 수량보다 많이 나가면 안 됩니다.
같은 회원이 버튼을 여러 번 눌러도 한 번만 처리되어야 합니다.

참고한 프로젝트: [f-lab-edu/cyber-monday](https://github.com/f-lab-edu/cyber-monday)
같은 주제를 NestJS로 다시 만들고, 문제가 깨지는 과정과 개선 수치를 기록합니다.

## 단계

한 번에 다 만들지 않습니다. 단계마다 깨뜨리고 고친 뒤 다음 단계로 넘어갑니다.
설계 문서(시나리오, ERD, Flow, API)는 3단계까지 먼저 쓰고, 코드는 단계 순서대로 만듭니다.

| 단계 | 범위 | 기능 문서 | 주요 Risk | 상태 |
|---|---|---|---|---|
| 1 | 로그인, 한정 수량 쿠폰 발급 | [인증](../features/auth/), [쿠폰](../features/coupon/) | R1~R5 | 설계 완료, 구현 전 |
| 2 | 상품 조회, 장바구니, 주문, 쿠폰·포인트 사용, 취소, 구매 확정, 자동 구매 확정 | [상품](../features/product/), [장바구니](../features/cart/), [주문](../features/order/), [포인트](../features/point/) | R6~R12 | 설계 완료, 구현 전 |
| 3 | Mock 결제, 포인트 비동기 적립, 자동 구매 확정 기준을 결제 승인 시각으로 변경 | [결제](../features/payment/), [포인트](../features/point/) | R13~R14 | 설계 초안 |

## 가정 트래픽

아래 수치는 가정입니다. 실제 서비스 데이터가 아닙니다.

| 항목 | 값 | 근거 |
|---|---|---|
| 행사 시작 직후 접속자 | 10만 명 | 가정. 시작 후 1분에 몰린다고 본다 |
| 쿠폰 발급 최대 요청량 | 3,000 RPS | 10만 명이 30초 안에 평균 1회 정도 누른다고 가정 (10만 ÷ 30초 ≈ 3,300) |
| 한정 수량 쿠폰 | 1종, 1만 장 | 수요(10만 명)가 수량의 10배인 상황 |
| 회원 데이터 | 10만 명 | 접속자 수와 같게 둔다 |
| 행사 상품 | 10종, 상품마다 재고 1,000개 | 가정. 쿠폰을 받은 1만 명이 상품 1만 개를 두고 경쟁한다 |
| 주문 최대 요청량 | 1,000 RPS | 가정. 쿠폰을 받은 1만 명이 10초 안에 평균 1회 주문한다고 본다 |

로컬 환경(MacBook + docker compose)에서 이 요청량을 실제로 낼 수 있는지는 확인하지 않았습니다 (미검증).
첫 실험에서 로컬 환경의 최대 처리량을 먼저 잽니다.

## 목표 수치

### 1단계: 쿠폰 발급

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 초과 발급 | 0건 | 부하 테스트 후 회원 쿠폰 수 ≤ 한정 수량 |
| 중복 발급 | 0건 | 같은 회원·같은 쿠폰의 회원 쿠폰이 2건 이상인 경우 수 |
| 수량 일치 | 오차 0 | Redis 발급 수 = 회원 쿠폰 수 (발급 수는 [집계 규칙](erd.md#집계-규칙)을 따른다) |
| 응답 시간 | p99 300ms 이하 | k6, 목표 RPS 유지 30초 |
| 서버 에러 | 5xx 0건 | k6 결과. 소진·중복 응답(409)은 정상 응답으로 본다 |

### 2단계: 주문 (초안)

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 초과 판매 | 0건 | 부하 테스트 후 상품마다 주문 수량 합 ≤ 처음 재고 |
| 재고 일치 | 오차 0 | 남은 재고 + 취소되지 않은 주문 수량 합 = 처음 재고 |
| 쿠폰 이중 사용 | 0건 | 취소되지 않은 주문 두 개 이상에 쓰인 회원 쿠폰 수 |
| 금액 일치 | 오차 0 | 주문의 금액 합계 = 주문 상품 금액의 합 |
| 중복 주문 | 0건 | 같은 멱등 키로 만들어진 주문이 2건 이상인 경우 수 |
| 응답 시간 | p99 500ms 이하 (가정) | k6, 주문 목표 RPS 유지 30초 |
| 서버 에러 | 5xx 0건 | 품절·쿠폰 사용 불가(409)는 정상 응답으로 본다 |

### 3단계: 결제와 포인트 (초안)

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 포인트 이중 적립 | 0건 | 주문 하나에 적립 내역이 2건 이상인 경우 수 |
| 포인트 잔액 일치 | 오차 0 | 회원마다 잔액 = 내역 금액의 합 |
| 결제 후 미반영 | 0건 | 결제 승인됐는데 주문이 완료도 실패도 아닌 상태로 남은 건수 (보상 후) |

## 범위 밖

- 실제 PG 결제 연동. 3단계에서 Mock 결제로 대체합니다.
- 프론트엔드. API와 부하 테스트 스크립트만 만듭니다.
- 회원가입, 비밀번호 찾기, 토큰 갱신, 소셜 로그인. 시드로 넣은 회원이 이메일과 비밀번호로 로그인만 합니다.
- 관리자 기능 (쿠폰 생성·발급 중단·회수·삭제, 상품 등록·판매 중지·삭제). 데이터는 시드로 넣고, 규칙만 [ERD](erd.md)와 [용어집](glossary.md)에 적어 둡니다.
- 배송지와 배송 상태.
- 부분 취소. 2단계는 주문 전체 취소만 합니다. 부분 취소에 필요한 금액은 지금부터 상품별로 기록합니다 ([ERD](erd.md#order_item-주문-상품)).
- 포인트 유효기간.
- 클라우드 배포. 로컬 측정이 끝난 뒤 따로 결정합니다.
