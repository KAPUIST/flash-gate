시드로 넣은 회원이 이메일과 비밀번호로 로그인하고, 받은 토큰으로 다른 API를 부릅니다.

## Risk

이 기능에는 Risk가 없습니다.

- 부하 테스트는 시작할 때 토큰을 한 번 받아 두고 다시 씁니다. 로그인은 몰리는 요청의 대상이 아닙니다.
- 로그인은 회원 데이터를 바꾸지 않습니다. 동시에 요청해도 깨질 상태가 없습니다.

회원가입, 비밀번호 찾기, 토큰 갱신, 소셜 로그인은 [범위 밖](../../reference/problem.md#범위-밖)입니다.

## 시나리오 1. 이메일과 비밀번호로 로그인

**사전 조건**: 시드로 넣은 회원이다. 탈퇴하지 않았다.

1. 회원이 이메일과 비밀번호를 보낸다.
2. 서버가 이메일로 탈퇴하지 않은 회원을 찾는다.
3. 서버가 비밀번호를 저장된 해시와 비교한다.
4. 맞으면 토큰을 준다. 회원은 "로그인되었습니다"를 본다.
   - 토큰은 1시간 동안 쓸 수 있다.
   - 토큰에는 회원 ID(`sub`), 생성 시각(`iat`), 만료 시각(`exp`)만 담는다. 이메일 같은 개인정보는 담지 않는다.
5. 이후 요청은 `Authorization: Bearer <토큰>` 헤더에 토큰을 담아 보낸다.

비밀번호 해시는 bcrypt나 argon2id 중 하나를 쓴다 (구현 시 확정).
모든 시드 회원은 미리 계산한 같은 해시를 쓴다. 10만 명을 하나씩 해시하면 시드가 오래 걸린다.

## 시나리오 2. 로그인 실패

**사전 조건**: 없음.

아래 경우는 모두 같은 응답을 준다. 회원은 "이메일 또는 비밀번호가 올바르지 않습니다"를 본다 (`401 AUTH_INVALID_CREDENTIALS`).

1. 그런 이메일의 회원이 없다.
2. 비밀번호가 틀렸다.
3. 탈퇴한 회원이다 (`deleted_at`이 있다).

같은 응답을 주는 이유: 어느 쪽이 틀렸는지 알려주면, 어떤 이메일이 가입되어 있는지 알아낼 수 있다.

- 이메일이 없을 때도 비밀번호 비교를 한 번 한다. 가짜 해시와 비교한다. 응답 시간 차이로 가입 여부를 알아내지 못하게 한다 (효과는 미검증).
- 이메일 형식이 아니거나 비밀번호가 비어 있으면 형식 오류다. 회원은 "요청 형식이 올바르지 않습니다"를 본다 (`400 COMMON_INVALID_REQUEST`).

## 시나리오 3. 토큰 없이, 잘못된 토큰, 만료된 토큰으로 요청

**사전 조건**: 로그인이 필요한 API를 부른다. 로그인이 필요 없는 API는 [API 공통 규칙](../../reference/api.md#인증)에 있다.

1. 아래 경우 서버는 요청을 처리하지 않는다. 회원은 "로그인이 필요합니다"를 본다 (`401 AUTH_UNAUTHORIZED`).
   - `Authorization` 헤더가 없다.
   - `Bearer` 형식이 아니다.
   - 서명이 맞지 않는다.
   - 만료 시각이 지났다.
2. 회원은 다시 로그인해서 새 토큰을 받는다.

**허용하는 지연·불일치**

- 토큰을 검사할 때 DB를 읽지 않는다. 서명과 만료 시각만 본다. 쿠폰 발급처럼 몰리는 요청마다 회원 조회가 붙지 않게 하려는 것이다.
- 그래서 탈퇴한 회원의 토큰도 만료될 때까지 최대 1시간 동안 통과한다. 탈퇴 기능은 범위 밖이라 지금은 이 상황이 생기지 않는다. 탈퇴 기능을 만들 때 다시 정한다.
