# 주문 (order)

회원이 고른 상품을 쿠폰과 포인트를 적용해 주문하고, 취소하거나 구매 확정합니다.
재고·쿠폰·포인트를 한 트랜잭션에서 함께 차감하고, 취소할 때 함께 복구합니다.

## 공통 규칙

| 규칙 | 값 |
|---|---|
| 한 주문의 상품 수 | 1~20종 (가정) |
| 상품 하나의 수량 | 1~99개 |
| 같은 상품 | 한 주문에 한 줄. 같은 상품을 두 줄로 보내면 400 |
| 쿠폰 | 상품마다 상품 쿠폰 최대 1장, 주문마다 주문 쿠폰 최대 1장. 같은 회원 쿠폰을 두 번 쓰지 못한다 |
| 포인트 | 5,000 이상일 때만 쓴다. 쿠폰 할인 뒤 금액의 10%까지. 잔액까지. 이 규칙은 [포인트 모듈](../point/)의 `PointPolicy`가 가진다 |
| 잠그는 순서 | 재고(상품 ID 오름차순) → 회원 쿠폰(ID 오름차순) → 주문 저장 → 포인트 잔액. 취소는 주문 행을 먼저 바꾼 뒤 같은 순서를 쓴다 |
| 다른 모듈 | 재고·쿠폰·포인트·장바구니는 그 모듈이 공개한 서비스로만 바꾼다. 같은 트랜잭션에 참여한다 ([ADR-0002](../../adr/0002-modular-monolith-with-one-port.md)) |

## 금액 계산 규칙

계산 순서는 **상품 쿠폰 → 주문 쿠폰 → 포인트**입니다. 이 순서는 주문서(시나리오 1, 2)와 주문하기(시나리오 3)가 같은 도메인 클래스로 계산합니다.

1. **주문 상품 금액(줄 금액)** = 단가 × 수량
2. **상품 쿠폰**: 줄 금액에 적용합니다. 줄 금액이 쿠폰의 최소 주문 금액 이상이어야 합니다. 할인은 줄 금액을 넘지 않습니다.
3. **상품 쿠폰 적용 후 합계** = 줄 금액 − 상품 쿠폰 할인의 합
4. **주문 쿠폰**: 3의 합계에 적용합니다. 3의 합계가 최소 주문 금액 이상이어야 합니다. 할인은 3의 합계를 넘지 않습니다.
5. **쿠폰 할인 뒤 금액** = 3의 합계 − 주문 쿠폰 할인
6. **포인트**: 5,000 이상, 5의 10% 이하(원 미만 버림), 잔액 이하. 5의 10%가 5,000보다 작으면, 즉 쿠폰 할인 뒤 금액이 50,000원 미만이면 포인트를 쓸 수 없습니다.
7. **결제 금액** = 상품 금액 − 할인 합계 − 포인트

**상품별로 나누기**: 주문 쿠폰 할인과 포인트는 각 줄의 "상품 쿠폰 적용 후 금액" 비율로 나눕니다. 원 미만은 버리고, 남은 원 단위는 그 금액이 가장 큰 줄에 더합니다. 가장 큰 줄이 여럿이면 상품 ID가 가장 작은 줄에 더합니다. 지금은 전체 취소만 하지만, 나중에 부분 취소 때 돌려줄 금액의 근거가 됩니다.

**지키는 규칙** (`R9`): `orders`의 할인·포인트·결제 금액은 `order_item` 같은 컬럼의 합과 같아야 합니다. 테이블을 넘는 규칙이라 CHECK로는 못 겁니다. 주문 도메인 클래스가 만들 때 검사하고, 아래 예시를 테스트 데이터로 고정합니다.

### 계산 예시

회원의 포인트 잔액은 12,000입니다.

| 상품 | 브랜드 | 단가 | 수량 | 줄 금액 | 고른 상품 쿠폰 |
|---|---|---|---|---|---|
| A (ID 11) 러닝화 | 나이키 | 59,000 | 1 | 59,000 | 회원 쿠폰 101: 나이키 브랜드 쿠폰, 정률 10%, 최대 5,000원, 최소 30,000원 |
| B (ID 12) 양말 | 나이키 | 3,000 | 3 | 9,000 | 없음 |
| C (ID 13) 티셔츠 | 아디다스 | 25,000 | 2 | 50,000 | 회원 쿠폰 102: 상품 C 쿠폰, 정액 3,000원, 최소 20,000원 |

주문 쿠폰: 회원 쿠폰 103, 정액 10,000원, 최소 100,000원. 쓸 포인트: 7,000.

1. 상품 쿠폰: A는 59,000 × 10% = 5,900인데 최대 5,000이라 **5,000**. C는 **3,000**.
2. 상품 쿠폰 적용 후: A 54,000, B 9,000, C 47,000. 합계 **110,000**.
3. 주문 쿠폰: 110,000 ≥ 100,000이라 쓸 수 있습니다. 할인 **10,000**.
4. 쿠폰 할인 뒤 금액: 100,000. 포인트 한도는 10,000. 7,000은 5,000 이상이고 한도와 잔액 이하라 쓸 수 있습니다.
5. 주문 쿠폰 10,000 나누기: A 10,000 × 54/110 = 4,909.09 → 4,909, B 818.18 → 818, C 4,272.72 → 4,272. 합 9,999. 남은 1원은 가장 큰 줄 A에 더해 **A 4,910**.
6. 포인트 7,000 나누기: A 3,436.36 → 3,436, B 572.72 → 572, C 2,990.90 → 2,990. 합 6,998. 남은 2원은 A에 더해 **A 3,438**.

## 시나리오 1. 주문서 보기

**사전 조건**: 로그인한 회원이다.

1. 회원이 장바구니에서 상품을 골라 "주문하기"를 누르거나, 상품 상세에서 "바로 구매"를 누른다.
   - 장바구니에서 오면 장바구니 항목 ID 목록을 보낸다. 수량은 장바구니에 담긴 수량이다.
   - 바로 구매면 상품 ID와 수량을 보낸다.
2. 주문서에 상품마다 지금 이름, 지금 가격, 줄 금액, 판매 상태(판매 중, 품절, 판매 중지)가 보인다.
   - 장바구니 항목이 없거나 다른 회원의 것이면 404를 본다.
   - 삭제된 상품이 들어 있으면 "판매하지 않는 상품입니다"로 표시한다. 주문하기는 할 수 없다.
3. 상품마다 쓸 수 있는 상품 쿠폰 목록이 보인다.
   - 회원의 회원 쿠폰 중 `ISSUED`이고 사용 기한이 지나지 않은 상품 쿠폰이다.
   - 쿠폰 대상(상품 또는 브랜드)에 그 상품이 들어 있어야 한다.
   - 줄 금액이 최소 주문 금액 이상이어야 한다.
4. 쓸 수 있는 주문 쿠폰 목록이 보인다. 최소 주문 금액은 상품 쿠폰을 적용하기 전 합계로 먼저 거른다. 고른 상품 쿠폰에 따라 다시 계산된다(시나리오 2).
5. 포인트 잔액과, 쓸 수 있는 최대 포인트가 보인다.
6. 아무것도 저장하지 않는다. 재고와 쿠폰을 잡아 두지 않는다.

**허용하는 지연·불일치**

- 주문서의 가격과 재고는 보는 순간의 값이다. 주문하기 전에 바뀔 수 있다. 바뀌면 시나리오 3에서 "금액이 바뀌었습니다"를 본다.

## 시나리오 2. 쿠폰과 포인트를 골라 금액 미리 보기

**사전 조건**: 시나리오 1의 주문서를 보고 있다.

1. 회원이 상품마다 상품 쿠폰을 하나씩 고르고, 주문 쿠폰을 하나 고르고, 쓸 포인트를 입력한다.
2. 서버가 [금액 계산 규칙](#금액-계산-규칙) 순서로 계산해 보여준다.
   - 상품별 상품 쿠폰 할인, 주문 쿠폰 할인, 포인트, 결제 금액
   - 상품별로 나눈 주문 쿠폰 할인과 포인트
3. 고른 쿠폰을 쓸 수 없으면 그 쿠폰 옆에 이유를 보여준다. 예: 최소 주문 금액 미달, 사용 기한 지남, 대상 상품 아님. 계산에서는 그 쿠폰을 빼고 보여준다.
4. 포인트가 5,000 미만이거나 한도를 넘으면 "포인트는 5,000부터, 최대 N원까지 쓸 수 있습니다"를 보여준다. "최대 적용"을 고르면 한도와 잔액 중 작은 값을 쓴다.
5. 아무것도 저장하지 않는다.

`R9`: 미리 보기와 주문하기가 같은 계산 클래스를 쓴다. 미리 보기에서도 주문 합계 = 상품별 합계를 검사한다.

## 시나리오 3. 주문하기

**사전 조건**: 시나리오 2에서 금액을 확인했다. 클라이언트는 주문서를 열 때 멱등 키를 하나 만들어 둔다.

1. 회원이 "결제하기"를 누른다. 요청에는 상품(또는 장바구니 항목), 고른 쿠폰, 포인트, 화면에서 본 결제 금액, 멱등 키가 들어 있다.
2. 서버가 지금 가격으로 다시 계산한다. 화면에서 본 결제 금액과 다르면 주문하지 않고 "금액이 바뀌었습니다. 다시 확인해 주세요"를 보여준다.
3. 한 트랜잭션에서 아래를 순서대로 한다. 하나라도 실패하면 전부 되돌린다.
   1. 상품이 판매 중이고 삭제되지 않았는지 확인한다. 아니면 "판매하지 않는 상품이 있습니다"를 본다.
   2. 재고를 상품 ID 오름차순으로 차감한다. 한 상품이라도 재고가 모자라면 "품절된 상품이 있습니다"를 본다. `R6` `R8`
   3. 고른 회원 쿠폰을 ID 오름차순으로 `USED`로 바꾼다. 이미 썼거나 다른 회원의 쿠폰이면 "쓸 수 없는 쿠폰입니다"를 본다. 사용 기한, 대상, 최소 주문 금액은 도메인 클래스가 먼저 확인한다. `R7`
   4. 주문, 주문 상품, 주문에 쓴 쿠폰을 저장한다. `R9`
   5. 포인트를 쓴다면 잔액을 차감하고 사용 내역을 남긴다. 내역에 주문 ID가 필요해서 주문을 저장한 뒤에 한다. 잔액이 모자라면 "포인트가 부족합니다"를 본다. `R11`
   6. 장바구니에서 왔으면 그 장바구니 항목을 지운다.
4. 주문이 완료되고 "주문이 완료되었습니다"와 주문 번호가 보인다. 상태는 `ORDERED`다.

동시에 일어나는 일:

- 마지막 재고 1개에 주문 두 개가 동시에 오면 하나만 성공한다. 다른 하나는 품절을 본다. `R6`
- 같은 회원이 같은 쿠폰으로 주문 두 개를 동시에 보내면 하나만 성공한다. 다른 하나는 "쓸 수 없는 쿠폰입니다"를 본다. `R7`
- 상품 A, B를 담은 주문과 B, A를 담은 주문이 동시에 와도 둘 다 같은 순서(A → B)로 잠그므로 데드락이 나지 않는다. `R8`

**허용하는 지연·불일치**

- 재고·쿠폰·포인트·장바구니는 주문과 같은 트랜잭션에서 바뀐다. 어긋나는 순간이 없다.
- 상품 목록·상세에 보이는 재고와 품절 표시는 몇 초 늦을 수 있다. 실제로 주문할 수 있는지는 주문할 때 정해진다.
- 주문 목록에는 주문 직후 바로 보인다.

## 시나리오 4. 같은 주문을 두 번 보냄

**사전 조건**: 시나리오 3의 요청을 보냈다.

1. 네트워크가 끊기거나 회원이 버튼을 두 번 눌러서, 같은 멱등 키로 요청이 한 번 더 온다.
2. 이미 그 키로 만든 주문이 있으면 새 주문을 만들지 않고 처음 주문을 그대로 보여준다. `R10`
3. 두 요청이 동시에 오면, 두 번째 요청은 첫 요청의 트랜잭션이 끝날 때까지 기다린다. 첫 요청이 성공하면 두 번째는 처음 주문을 보여준다. 첫 요청이 실패하면 두 번째가 새로 처리된다.
4. 첫 요청이 품절 같은 이유로 실패했다면 아무것도 저장되지 않는다. 같은 키로 다시 보내면 새로 처리한다.
5. 같은 키로 내용이 다른 요청을 보내도 처음 주문을 보여준다. 요청 내용은 비교하지 않는다. 클라이언트는 주문서를 열 때마다 새 키를 만든다 ([API 공통 규칙](../../reference/api.md#멱등성)).

---

## 시나리오 5. 내 주문 목록·상세 보기

**사전 조건**: 로그인한 회원이다.

1. 회원이 "주문 내역"을 누르면 최근 주문부터 목록이 보인다. 주문 일시, 상태, 대표 상품 이름, 결제 금액이 보인다.
2. 주문을 누르면 상세가 보인다. 상품마다 주문할 때의 이름·가격·수량, 상품 쿠폰 할인, 나눈 주문 쿠폰 할인과 포인트, 결제 금액이 보인다. 쓴 쿠폰 목록도 보인다.
3. 다른 회원의 주문이면 404를 본다.
4. 상품이 나중에 가격이 바뀌거나 삭제돼도, 주문 내역은 주문할 때의 값 그대로 보인다. 주문 내역은 주문 상품에 복사한 값만 읽는다.

---

## 시나리오 6. 주문 취소

**사전 조건**: 회원의 주문이 `ORDERED` 상태다.

1. 회원이 주문 상세에서 "주문 취소"를 누른다.
2. 한 트랜잭션에서 아래를 한다.
   1. 주문을 `CANCELED`로 바꾼다. 주문이 `ORDERED`가 아니면(이미 취소됐거나 구매 확정됐으면) "취소할 수 없는 주문입니다"를 본다.
   2. 재고를 상품 ID 오름차순으로 되돌린다.
   3. 쓴 회원 쿠폰을 `ISSUED`로 되돌린다. 사용 기한이 지났어도 되돌린다. 만료는 계산하므로 다시 쓸 수는 없다.
   4. 쓴 포인트를 되돌리고 사용 취소 내역을 남긴다.
3. 주문 상태가 "주문 취소"로 바뀐 것이 보인다.

- 같은 주문을 동시에 두 번 취소하면 하나만 성공한다. 다른 하나는 "취소할 수 없는 주문입니다"를 본다.
- 취소와 구매 확정이 동시에 오면 먼저 커밋된 쪽만 성공한다.
- 지금은 주문 전체 취소만 한다. 부분 취소는 나중에 만든다. 필요한 금액은 이미 상품별로 기록돼 있다.

**허용하는 지연·불일치**

- 없음. 주문·재고·쿠폰·포인트가 한 트랜잭션에서 바뀐다.

---

## 시나리오 7. 구매 확정

**사전 조건**: 회원의 주문이 `ORDERED` 상태다.

1. 회원이 주문 상세에서 "구매 확정"을 누른다.
2. 주문을 `CONFIRMED`로 바꾼다. 주문이 `ORDERED`가 아니면 "구매 확정할 수 없는 주문입니다"를 본다.
3. 결제 금액의 5%(원 미만 버림)만큼 포인트가 쌓인다. 결제 금액이 0원이면 쌓이지 않는다. 예: 결제 금액 93,000원 → 4,650 포인트
4. 확정된 주문은 취소할 수 없다.

- 2단계는 확정과 적립을 같은 트랜잭션에서 한다.
- 3단계는 확정만 하고, 적립은 비동기로 한다 ([포인트 기능](../point/), [결제 기능](../payment/)).

**허용하는 지연·불일치**

- 2단계: 없음.
- 3단계: 확정 뒤 포인트가 몇 초 늦게 쌓일 수 있다.

---

## 시나리오 8. (시스템) 자동 구매 확정

**사전 조건**: 주문한 지 7일이 지났는데 `ORDERED` 상태인 주문이 있다 (7일은 가정).

1. 배치가 정해진 주기로 돈다 (주기 1시간, 가정).
2. 대상 주문을 주문 ID 순서로 100건씩 읽는다 (가정).
3. 주문마다 따로 트랜잭션을 열어 시나리오 7과 같은 일을 한다.
4. 그 사이 회원이 취소했거나 확정했으면 상태 조건에 걸려 바뀌지 않는다. 그 주문은 건너뛴다.
5. 한 주문이 실패해도 다른 주문은 계속 처리한다. 실패한 주문은 다음 주기에 다시 대상이 된다.

**허용하는 지연·불일치**

- 7일이 지난 주문이 배치 주기만큼 늦게 확정될 수 있다.
