# 포인트 (point)

구매 확정된 주문의 결제 금액에 따라 포인트를 쌓고, 다음 주문에서 돈처럼 씁니다.

| 항목 | 내용 |
|---|---|
| 단계 | 2단계 (적립을 비동기로 바꾸는 것은 3단계) ([문제 정의](../../reference/problem.md#단계)) |
| 코드 | `src/point/` (아직 없음) |
| 상태 | 설계 완료, 구현 전 |
| 관련 테이블 | `member_point`, `point_history` ([ERD](../../reference/erd.md#member_point-point_history-포인트)) |
| 관련 흐름 | [유저 플로우](../../reference/user-flows.md#포인트-문서) 포인트 1~5 |

## 규칙

참고 프로젝트([f-lab-edu/cyber-monday](https://github.com/f-lab-edu/cyber-monday))의 시나리오에서 가져왔습니다.

| 규칙 | 값 | 비고 |
|---|---|---|
| 최소 사용 | 한 번에 5,000포인트 이상 쓸 때만 쓸 수 있다 | (해석) 참고 프로젝트는 "5천 원부터 사용할 수 있다"고만 적었다. 잔액 기준이 아니라 한 주문에서 쓰는 양 기준으로 읽었다 |
| 최대 사용 | 쿠폰 할인 뒤 금액의 10%까지 | 원 미만은 버린다. 예: 쿠폰 할인 뒤 45,990원 → 최대 4,599포인트 |
| 잔액 | 잔액보다 많이 쓸 수 없다 | DB가 잔액 0 미만을 막는다 (`R11`) |
| 적립 | 구매 확정된 주문의 결제 금액 × 5%, 원 미만 버림 | 예: 결제 금액 41,391원 → 2,069포인트 |
| 적립 시점 | 구매 확정 때 | 확정된 주문은 취소할 수 없어서 적립을 되돌릴 일이 없다 |
| 취소 | 주문이 취소되면 그 주문에 쓴 포인트를 돌려준다 | 내역 종류 `USE_CANCEL` |
| 유효기간 | 없음 | [범위 밖](../../reference/problem.md#범위-밖) |
| 단위 | 1포인트 = 1원 | |

- 적립 금액에 쓰는 결제 금액은 포인트를 쓴 뒤의 금액(`orders.payment_amount`)입니다. 포인트로 낸 금액에는 다시 포인트를 쌓지 않습니다.
- 최소 사용과 최대 사용이 부딪힐 수 있습니다. 쿠폰 할인 뒤 금액이 50,000원 미만이면 10% 한도가 5,000포인트보다 작아서 포인트를 쓸 수 없습니다. 이것도 규칙대로입니다.
- 이 규칙들은 바뀔 수 있는 정책이라 도메인 클래스(`PointPolicy`)에만 둡니다. DB는 "잔액 ≥ 0"과 "내역 부호" 같은 바뀌지 않는 사실만 지킵니다 ([ERD 공통 규칙](../../reference/erd.md#공통-규칙)).

## Risk

Risk ID는 프로젝트 전체에서 이어서 매깁니다. 전체 결과는 [README 핵심 결과](../../../README.md#2-핵심-결과) 표에 모읍니다.

| ID | 깨지는 지점 | 시나리오 | 상태 | 근거 |
|---|---|---|---|---|
| R11 | 같은 회원의 주문 두 개가 동시에 같은 잔액을 쓰면, 잔액보다 많은 포인트가 쓰이거나 잔액이 0 미만이 된다 | 3 | 미해결 | |
| R12 | 구매 확정 처리나 비동기 적립 메시지가 두 번 실행되면, 한 주문에 포인트가 두 번 쌓인다 | 5 | 미해결 | |

상태 값: `미해결` → `재현함` (Before 수치 있음) → `해결` (After 수치 있음) / `보류`

## 시나리오 1. 포인트 잔액 보기

**사전 조건**: 로그인한 회원이다.

1. 회원이 "내 포인트" 화면을 연다.
2. 지금 잔액이 보인다.
   - 한 번도 적립받은 적이 없으면 잔액 0이 보인다. `member_point` 행이 없어도 에러가 아니다.
3. 잔액 옆에 "다음 주문에서 5,000포인트 이상부터 쓸 수 있습니다"가 보인다.

---

## 시나리오 2. 포인트 내역 보기

**사전 조건**: 로그인한 회원이다.

1. 회원이 "포인트 내역"을 연다.
2. 최근 내역부터 보인다. 내역마다 종류, 금액, 그 뒤 잔액, 시각, 관련 주문이 보인다.
   - 종류: 적립(`EARN`), 사용(`USE`), 사용 취소(`USE_CANCEL`)
   - 적립과 사용 취소는 `+`, 사용은 `-`로 보인다.
3. 아래로 내리면 다음 페이지가 이어서 보인다. 행사 중 새 내역이 생겨도 이미 본 내역이 겹치거나 빠지지 않는다 (커서 방식).
4. 종류로 거를 수 있다. 예: 적립만 보기

---

## 시나리오 3. 주문에 포인트 쓰기

**사전 조건**: 로그인한 회원이 주문서를 열었다 ([주문 시나리오 1](../order/)). 쿠폰을 고른 뒤다.

1. 주문서에 "쓸 수 있는 포인트"가 보인다. 값은 `min(잔액, 쿠폰 할인 뒤 금액의 10%)`이다.
   - 이 값이 5,000 미만이면 "포인트를 쓸 수 없습니다"가 보이고 입력칸이 잠긴다.
2. 회원이 쓸 포인트를 입력한다. "최대 사용" 버튼을 누르면 쓸 수 있는 포인트가 그대로 들어간다.
3. 주문서가 결제 금액을 다시 계산해서 보여준다 ([주문 시나리오 2](../order/)).
4. 회원이 주문한다. 주문 트랜잭션 안에서 잔액이 차감되고 사용 내역이 남는다 ([주문 시나리오 3](../order/)).
   - 5,000포인트 미만을 입력하면 "포인트는 5,000포인트 이상부터 쓸 수 있습니다"가 보인다. `POINT_BELOW_MINIMUM_USE`
   - 10% 한도를 넘게 입력하면 "포인트는 쿠폰 할인 뒤 금액의 10%까지 쓸 수 있습니다"가 보인다. `POINT_EXCEEDS_LIMIT`
   - 주문서를 연 뒤 다른 주문에서 포인트를 써서 잔액이 모자라면, 주문이 실패하고 "포인트가 부족합니다"가 보인다. 재고·쿠폰 차감도 함께 취소된다. `POINT_INSUFFICIENT`
   - 같은 회원이 두 기기에서 동시에 주문해도 잔액보다 많이 쓰이지 않는다. 늦게 커밋된 주문은 잔액 부족으로 실패한다. `R11`

**허용하는 지연·불일치**

- 주문서에 보인 "쓸 수 있는 포인트"는 주문 버튼을 누를 때 달라질 수 있다. 주문할 때 다시 검사한다.
- 잔액은 어떤 순간에도 0 미만이 될 수 없다.

---

## 시나리오 4. 주문 취소로 포인트 돌려받기

**사전 조건**: 포인트를 쓴 주문이 `ORDERED` 상태다.

1. 회원이 주문을 취소한다 ([주문 시나리오 6](../order/)).
2. 취소 트랜잭션 안에서 그 주문에 쓴 포인트만큼 잔액이 늘고, 사용 취소(`USE_CANCEL`) 내역이 남는다.
3. 포인트 내역에 "+N 사용 취소"가 보인다.
   - 포인트를 쓰지 않은 주문이면 포인트는 아무것도 바뀌지 않는다.
   - 같은 주문의 취소가 두 번 와도 포인트는 한 번만 돌려준다. 주문 상태 조건(`WHERE status = 'ORDERED'`)이 두 번째 취소를 막고, `UNIQUE(order_id, type)`이 한 번 더 막는다.
   - 구매 확정된 주문은 취소할 수 없다. 그래서 적립된 포인트를 되돌리는 일은 없다.

---

## 시나리오 5. 구매 확정으로 포인트 적립

**사전 조건**: 주문이 `ORDERED` 상태다.

1. 회원이 구매 확정을 누르거나, 주문 7일 뒤 자동 확정 배치가 확정한다 ([주문 시나리오 7, 8](../order/)).
2. 결제 금액의 5%가 포인트로 쌓이고 적립(`EARN`) 내역이 남는다.
   - 결제 금액의 5%가 0이면(결제 금액 19원 이하) 적립하지 않고 내역도 남기지 않는다.
   - 확정 처리가 두 번 실행돼도 포인트는 한 번만 쌓인다. `R12`
3. **2단계**: 확정과 같은 트랜잭션에서 적립한다. 확정되면 포인트 내역에 바로 보인다.
4. **3단계**: 확정 트랜잭션은 "적립할 것" 기록(outbox)만 남긴다. 워커가 그 기록을 읽어 비동기로 적립한다 ([Flow](flows.md#시나리오-5-구매-확정으로-포인트-적립)).
   - 워커가 같은 메시지를 두 번 받아도 한 번만 쌓인다. 두 번째는 이미 처리한 것으로 보고 넘어간다. `R12`

**허용하는 지연·불일치**

- 3단계에서는 확정 뒤 포인트가 몇 초 늦게 쌓일 수 있다 (참고 프로젝트도 "수 초 지연될 수 있다"고 적었다).
- 확정된 주문의 적립 내역은 결국 정확히 하나여야 한다. 0개로 남거나 2개가 되면 안 된다.
- 잔액은 어떤 순간에도 내역 금액의 합과 같다.

## 다른 모듈이 부르는 서비스

포인트 사용·복구·적립에는 공개 API가 없습니다. 주문 모듈이 포인트 모듈의 `index.ts`가 공개한 서비스를 함수로 부릅니다 ([모듈 사이의 규칙](../../reference/conventions.md#모듈-사이의-규칙)).
모든 메서드는 호출한 쪽의 트랜잭션에 참여합니다 (`@nestjs-cls/transactional`).

| 메서드 | 입력 | 하는 일 | 에러 |
|---|---|---|---|
| `getBalance(memberId)` | 회원 ID | 잔액. 행이 없으면 0 | |
| `calculateUsableAmount(memberId, amountAfterCoupons)` | 회원 ID, 쿠폰 할인 뒤 금액 | `min(잔액, 10% 한도)`. 5,000 미만이면 0 | |
| `use(memberId, orderId, amount, amountAfterCoupons)` | 회원 ID, 주문 ID, 쓸 포인트, 쿠폰 할인 뒤 금액 | 규칙 검사 → 조건부 차감 → `USE` 내역 | `POINT_BELOW_MINIMUM_USE`, `POINT_EXCEEDS_LIMIT`, `POINT_INSUFFICIENT` |
| `cancelUse(memberId, orderId)` | 회원 ID, 주문 ID | 그 주문의 `USE` 금액만큼 되돌림 → `USE_CANCEL` 내역. 쓴 적이 없으면 아무것도 하지 않음 | |
| `earn(memberId, orderId, paymentAmount)` | 회원 ID, 주문 ID, 결제 금액 | 5% 적립 → `EARN` 내역. 적립액이 0이면 아무것도 하지 않음 | 같은 주문의 `EARN` 내역이 이미 있으면 UNIQUE 위반 (`R12`). 2단계: 확정 트랜잭션 전체가 롤백된다. 확정은 주문 상태 조건이 먼저 막으므로 정상 흐름에서는 일어나지 않는다. 3단계: 워커가 롤백한 뒤 이미 처리된 것으로 보고 메시지를 완료(ack)한다 |

- `amount`가 0이면 `use`는 아무것도 하지 않습니다. 포인트를 쓰지 않는 주문도 같은 경로로 부를 수 있게 합니다.
- 에러는 도메인 에러로 던지고, 주문 API가 `409`로 바꿔 응답합니다 ([API](api.md#다른-기능의-응답에-쓰이는-에러)).
