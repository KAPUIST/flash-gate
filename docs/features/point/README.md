# 포인트 (point)

구매 확정된 주문의 결제 금액에 따라 포인트를 쌓고, 다음 주문에서 돈처럼 씁니다.

| 항목 | 내용 |
|---|---|
| 만드는 순서 | 주문. 적립 이벤트의 전달 방식을 outbox, Kafka로 바꾸는 것은 이벤트 범위 ([문제 정의](../../reference/problem.md#만드는-순서)) |
| 코드 | `src/point/` (아직 없음) |
| 상태 | 설계 완료, 구현 전 |
| 관련 테이블 | `member_point`, `point_history` ([ERD](../../reference/erd.md#member_point-point_history-포인트)) |
| 관련 흐름 | [유저 플로우](../../reference/user-flows.md#포인트-문서)의 포인트 흐름 5가지 전체 |

## 규칙

| 규칙 | 값 | 비고 |
|---|---|---|
| 최소 사용 | 한 번에 5,000포인트 이상 쓸 때만 쓸 수 있습니다 | 기준은 잔액이 아니라 한 주문에서 쓰는 양입니다 |
| 최대 사용 | 쿠폰 할인 뒤 금액의 10%까지 | 원 미만은 버립니다. 예를 들어 쿠폰 할인 뒤 45,990원이면 최대 4,599포인트입니다 |
| 잔액 | 잔액보다 많이 쓸 수 없습니다 | DB가 잔액 0 미만을 막습니다 (포인트 이중 사용) |
| 적립 | 구매 확정된 주문의 결제 금액 × 5%, 원 미만 버림 | 예를 들어 결제 금액 41,391원이면 2,069포인트입니다 |
| 적립 시점 | 구매 확정 때 | 확정된 주문은 취소할 수 없어서 적립을 되돌릴 일이 없습니다 |
| 취소 | 주문이 취소되면 그 주문에 쓴 포인트를 돌려줍니다 | 내역 종류 `USE_CANCEL` |
| 유효기간 | 없음 | [범위 밖](../../reference/problem.md#범위-밖) |
| 단위 | 1포인트 = 1원 | |

- 적립 금액에 쓰는 결제 금액은 포인트를 쓴 뒤의 금액(`orders.payment_amount`)입니다. 포인트로 낸 금액에는 다시 포인트를 쌓지 않습니다.
- 최소 사용과 최대 사용이 부딪힐 수 있습니다. 쿠폰 할인 뒤 금액이 50,000원 미만이면 10% 한도가 5,000포인트보다 작아서, 규칙대로 포인트를 쓸 수 없습니다.
- 이 규칙은 바뀔 수 있는 정책이라 도메인 클래스(`PointPolicy`)에만 둡니다. DB는 "잔액 ≥ 0"과 "내역 부호" 같은 바뀌지 않는 사실만 지킵니다 ([ERD 공통 규칙](../../reference/erd.md#공통-규칙)).

## Risk

전체 결과는 [README 결과 표](../../../README.md#2-결과)에 모읍니다.

| Risk | 깨지는 지점 | 시나리오 | 상태 | 근거 |
|---|---|---|---|---|
| 포인트 이중 사용 | 같은 회원의 주문 두 개가 동시에 같은 잔액을 쓸 때 잔액보다 많은 포인트가 쓰이거나 잔액이 0 미만이 되는 문제 | [주문에 포인트 쓰기](#시나리오-3-주문에-포인트-쓰기) | 미해결 | |
| 포인트 적립 누락 | 구매 확정됐는데 적립 이벤트가 사라져서 포인트가 끝내 안 쌓이는 문제 | [구매 확정으로 포인트 적립](#시나리오-5-구매-확정으로-포인트-적립) | 미해결 | |
| 포인트 이중 적립 | 구매 확정 처리나 적립 이벤트가 두 번 실행될 때 한 주문에 포인트가 두 번 쌓이는 문제 | [구매 확정으로 포인트 적립](#시나리오-5-구매-확정으로-포인트-적립) | 미해결 | |

상태는 `미해결`에서 `재현함`, `해결` 순서로 바뀝니다. 재현함은 Before 수치가, 해결은 After 수치가 있는 상태이고, 미루는 Risk는 `보류`로 둡니다.

## 시나리오 1. 포인트 잔액 보기

사전 조건: 로그인한 회원입니다.

1. 회원이 "내 포인트" 화면을 엽니다.
2. 지금 잔액이 보입니다.
   - 한 번도 적립받은 적이 없으면 잔액 0이 보이고, `member_point` 행이 없어도 에러가 아닙니다.
3. 잔액 옆에 "다음 주문에서 5,000포인트 이상부터 쓸 수 있습니다"가 보입니다.

---

## 시나리오 2. 포인트 내역 보기

사전 조건: 로그인한 회원입니다.

1. 회원이 "포인트 내역"을 엽니다.
2. 최근 내역부터 보이고, 내역마다 종류, 금액, 그 뒤 잔액, 시각, 관련 주문이 보입니다.
   - 종류는 적립, 사용, 사용 취소이고, 값은 순서대로 `EARN`, `USE`, `USE_CANCEL`입니다.
   - 적립과 사용 취소는 `+`, 사용은 `-`로 보입니다.
3. 아래로 내리면 다음 페이지가 이어서 보입니다. 커서 방식이라 행사 중 새 내역이 생겨도 이미 본 내역이 겹치거나 빠지지 않습니다.
4. 적립만 보기처럼 종류로 거를 수 있습니다.

---

## 시나리오 3. 주문에 포인트 쓰기

사전 조건: 로그인한 회원이 주문서를 열고 쿠폰을 고른 상태입니다 ([주문 기능의 주문서 보기](../order/)).

1. 주문서에 "쓸 수 있는 포인트"가 보이고, 값은 `min(잔액, 쿠폰 할인 뒤 금액의 10%)`입니다.
   - 이 값이 5,000 미만이면 "포인트를 쓸 수 없습니다"가 보이고 입력칸이 잠깁니다.
2. 회원이 쓸 포인트를 입력합니다. "최대 사용" 버튼을 누르면 쓸 수 있는 포인트가 그대로 들어갑니다.
3. 주문서가 결제 금액을 다시 계산해서 보여줍니다 ([주문 기능의 쿠폰과 포인트를 골라 금액 미리 보기](../order/)).
4. 회원이 주문하면 주문 트랜잭션 안에서 잔액이 차감되고 사용 내역이 남습니다 ([주문 기능의 주문하기](../order/)).
   - 5,000포인트 미만을 입력하면 "포인트는 5,000포인트 이상부터 쓸 수 있습니다"가 보입니다. `POINT_BELOW_MINIMUM_USE`
   - 10% 한도를 넘게 입력하면 "포인트는 쿠폰 할인 뒤 금액의 10%까지 쓸 수 있습니다"가 보입니다. `POINT_EXCEEDS_LIMIT`
   - 주문서를 연 뒤 다른 주문에서 포인트를 써서 잔액이 모자라면 주문이 실패하고 "포인트가 부족합니다"가 보입니다. 재고·쿠폰 차감도 함께 취소됩니다. `POINT_INSUFFICIENT`
   - 같은 회원이 두 기기에서 동시에 주문해도 잔액보다 많이 쓰이지 않고, 늦게 커밋된 주문은 잔액 부족으로 실패합니다. (포인트 이중 사용)

#### 허용하는 지연·불일치

- 주문서에 보인 "쓸 수 있는 포인트"는 주문 버튼을 누를 때 달라질 수 있어서, 주문할 때 다시 검사합니다.
- 잔액은 어떤 순간에도 0 미만이 될 수 없습니다.

---

## 시나리오 4. 주문 취소로 포인트 돌려받기

사전 조건: 포인트를 쓴 주문이 `ORDERED` 상태입니다.

1. 회원이 주문을 취소합니다 ([주문 기능의 주문 취소](../order/)).
2. 취소 트랜잭션 안에서 그 주문에 쓴 포인트만큼 잔액이 늘고, 사용 취소(`USE_CANCEL`) 내역이 남습니다.
3. 포인트 내역에 "+N 사용 취소"가 보입니다.
   - 포인트를 쓰지 않은 주문이면 포인트는 아무것도 바뀌지 않습니다.
   - 같은 주문의 취소가 두 번 와도 포인트는 한 번만 돌려줍니다. 주문 상태 조건(`WHERE status = 'ORDERED'`)이 두 번째 취소를 막고, `UNIQUE(order_id, type)`이 한 번 더 막습니다.
   - 구매 확정된 주문은 취소할 수 없어서 적립된 포인트를 되돌리는 일은 없습니다.

---

## 시나리오 5. 구매 확정으로 포인트 적립

사전 조건: 주문이 `ORDERED` 상태입니다.

1. 회원이 구매 확정을 누르거나, 주문 7일 뒤 자동 확정 배치가 확정합니다 ([주문 기능의 구매 확정과 자동 구매 확정](../order/)).
2. 확정이 커밋되면 주문 모듈이 구매 확정됨(`ORDER_CONFIRMED`) 이벤트를 보내고, 포인트 모듈의 구독자가 받아서 적립합니다.
3. 결제 금액의 5%가 포인트로 쌓이고 적립(`EARN`) 내역이 남습니다.
   - 결제 금액의 5%가 0이면(결제 금액 19원 이하) 적립하지 않고 내역도 남기지 않습니다.
   - 확정 처리나 이벤트가 두 번 실행돼도 포인트는 한 번만 쌓입니다. (포인트 이중 적립)
4. 이벤트 전달은 프로세스 안, outbox, Kafka 순서로 바꿉니다. 프로세스 안 이벤트에서는 서버가 죽으면 적립이 빠지는 문제를 재현하고, outbox로 고칩니다. (포인트 적립 누락, [Flow](flows.md#시나리오-5-구매-확정으로-포인트-적립))

#### 허용하는 지연·불일치

- 포인트가 확정보다 몇 초 늦게 쌓일 수 있습니다.
- 확정된 주문의 적립 내역은 결국 하나만 있어야 하고, 0개로 남거나 2개가 되면 안 됩니다.
- 잔액은 어떤 순간에도 내역 금액의 합과 같습니다.

## 다른 모듈이 부르는 서비스

포인트 사용·복구·적립에는 공개 API가 없습니다. 사용과 복구는 주문 모듈이 포인트 모듈의 `index.ts`가 공개한 서비스를 함수로 부르고, 적립은 포인트 모듈 안의 구독자가 부릅니다 ([모듈 사이의 규칙](../../reference/conventions.md#모듈-사이의-규칙)).
모든 메서드는 호출한 쪽의 트랜잭션에 참여합니다 (`@nestjs-cls/transactional`).

| 메서드 | 입력 | 하는 일 | 에러 |
|---|---|---|---|
| `getBalance(memberId)` | 회원 ID | 잔액. 행이 없으면 0 | |
| `calculateUsableAmount(memberId, amountAfterCoupons)` | 회원 ID, 쿠폰 할인 뒤 금액 | `min(잔액, 10% 한도)`. 5,000 미만이면 0 | |
| `use(memberId, orderId, amount, amountAfterCoupons)` | 회원 ID, 주문 ID, 쓸 포인트, 쿠폰 할인 뒤 금액 | 규칙을 검사하고 조건부로 차감한 뒤 `USE` 내역을 남깁니다 | `POINT_BELOW_MINIMUM_USE`, `POINT_EXCEEDS_LIMIT`, `POINT_INSUFFICIENT` |
| `cancelUse(memberId, orderId)` | 회원 ID, 주문 ID | 그 주문의 `USE` 금액만큼 되돌리고 `USE_CANCEL` 내역을 남깁니다. 쓴 적이 없으면 아무것도 하지 않습니다 | |
| `earn(memberId, orderId, paymentAmount)` | 회원 ID, 주문 ID, 결제 금액 | 5%를 적립하고 `EARN` 내역을 남깁니다. 적립액이 0이면 아무것도 하지 않습니다 | 같은 주문의 `EARN` 내역이 이미 있으면 UNIQUE 위반 (포인트 이중 적립). 구독자는 적립 트랜잭션을 롤백하고 이미 처리된 것으로 보고 성공으로 끝냅니다 |

- `amount`가 0이면 `use`는 아무것도 하지 않아서, 포인트를 쓰지 않는 주문도 같은 경로로 부를 수 있습니다.
- 에러는 도메인 에러로 던지고, 주문 API가 `409`로 바꿔 응답합니다 ([API](api.md#다른-기능의-응답에-쓰이는-에러)).
