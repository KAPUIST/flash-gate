# 쿠폰 (coupon)

행사 시작 직후 요청이 몰려도 한정 수량 쿠폰을 정해진 수량만큼만 발급합니다.
발급 결정은 Redis가 하고, DB는 회원 쿠폰을 기록합니다 ([Redis가 쿠폰 발급을 결정](../../adr/0001-redis-decides-coupon-issue.md)).

| 항목 | 내용 |
|---|---|
| 만드는 순서 | 쿠폰 발급 (상품 쿠폰 대상 테이블은 주문을 만들 때) ([문제 정의](../../reference/problem.md#만드는-순서)) |
| 코드 | `src/coupon/` (아직 없음) |
| 상태 | 설계 완료, 구현 전 |
| 관련 테이블 | [`coupon`](../../reference/erd.md#coupon-쿠폰), [`member_coupon`](../../reference/erd.md#member_coupon-회원-쿠폰), [`coupon_product`, `coupon_brand`](../../reference/erd.md#coupon_product-coupon_brand-상품-쿠폰의-대상) |
| Redis 키 | `coupon:{id}:members`, `coupon:{id}:count` ([ERD](../../reference/erd.md#redis-키)) |

## Risk

전체 결과는 [README 결과 표](../../../README.md#2-결과)에 모읍니다.

| Risk | 깨지는 지점 | 시나리오 | 증명 방법 | 상태 | 근거 |
|---|---|---|---|---|---|
| 초과 발급 | 마지막 수량에 여러 명이 동시에 요청할 때 한정 수량을 넘는 발급 | 쿠폰 발급받기 | 부하 실험: 회원 쿠폰 수 ≤ 한정 수량 | 미해결 | |
| 같은 회원 중복 요청 | 같은 회원의 중복 요청이 409로 끝나지 않고 5xx나 수량 어긋남으로 이어지는 문제 | 쿠폰 발급받기 | 동시성 테스트: 같은 회원 50건 동시 요청에 201 1건, 409 49건, 5xx 0건 | 미해결 | |
| 발급 수 불일치 | Redis 발급 수와 회원 쿠폰 기록의 어긋남 | 쿠폰 발급받기, 발급 준비와 Redis 복구 | 부하 실험 후 Redis 발급 수 = 회원 쿠폰 수 | 미해결 | |
| 발급 지연·에러 | 요청이 몰릴 때 응답 지연과 서버 에러 | 쿠폰 발급받기 | 부하 실험: p99 300ms 이하, 5xx 0건 | 미해결 | |
| Redis 재시작 | Redis 재시작으로 발급 수가 0부터 다시 시작될 때의 초과 발급 | 발급 준비와 Redis 복구 | Redis 재시작을 끼운 부하 실험 | 미해결 | |

상태는 `미해결`에서 `재현함`, `해결` 순서로 바뀝니다. 재현함은 Before 수치가, 해결은 After 수치가 있는 상태이고, 미루는 Risk는 `보류`로 둡니다.

- `UNIQUE(member_id, coupon_id)`가 있어서 같은 회원 중복 요청에서 중복 발급은 처음부터 DB가 막고, 회원 쿠폰이 2장 생기는 일은 없습니다. 깨질 수 있는 곳은 응답입니다. UNIQUE 위반을 처리하지 않으면 409 대신 500이 나가고 Redis 수량도 어긋나서, 부하 실험이 아니라 동시성 테스트로 확인합니다.
- Redis 재시작 Risk를 고칠 후보는 발급 준비 표시 키가 없으면 거절하기, Lua로 확인과 증가를 묶기, AOF로 Redis 영속화하기, `issue_seq`로 순번 기록하기입니다. `issue_seq`는 실패 보상으로 발급 수를 줄이면 같은 순번이 다시 나가 UNIQUE와 부딪힙니다 ([ERD 나중에 검토할 것](../../reference/erd.md#나중에-검토할-것)).

## 시나리오 1. 행사 쿠폰 목록 보기

사전 조건: 없습니다. 로그인하지 않아도 볼 수 있습니다.

1. 회원이 행사 페이지를 엽니다.
2. 받을 수 있는 쿠폰과 곧 열릴 쿠폰이 보입니다.
   - 발급 중단(`STOPPED`)된 쿠폰과 삭제된 쿠폰은 보이지 않습니다.
   - 발급 기간이 끝난 쿠폰도 보이지 않습니다.
3. 쿠폰마다 할인 내용, 발급 기간, 사용 기한, 남은 수량이 보입니다.
   - 남은 수량은 `한정 수량 − Redis 발급 수`이고, 0보다 작으면 0으로 보입니다.
   - 발급 준비 전(Redis 키가 없을 때)에는 남은 수량이 한정 수량과 같습니다.
   - 남은 수량은 대략적인 값이라 처리 중인 요청 때문에 실제보다 잠깐 적게 보일 수 있습니다.
4. 쿠폰마다 곧 열림, 받을 수 있음, 소진 가운데 하나의 상태가 보입니다.
   - 상태는 저장하지 않고 발급 기간과 남은 수량으로 계산합니다.
5. 상품 쿠폰이면 쓸 수 있는 상품과 브랜드가 함께 보입니다. (주문을 만들 때)

## 시나리오 2. 쿠폰 발급받기

관련 Risk: 초과 발급, 같은 회원 중복 요청, 발급 수 불일치, 발급 지연·에러

사전 조건: 로그인한 회원입니다.

1. 회원이 행사 페이지에서 "쿠폰 받기" 버튼을 누릅니다.
2. 서버는 아래 순서로 확인하고, 앞에서 걸리면 뒤는 확인하지 않습니다.
   1. 쿠폰이 없거나 삭제됐으면 "쿠폰을 찾을 수 없습니다"가 보입니다. `404 COUPON_NOT_FOUND`
   2. 발급 중단된 쿠폰이면 "발급이 중단된 쿠폰입니다"가 보입니다. `409 COUPON_ISSUE_STOPPED`
   3. 발급 기간 전이면 "아직 발급 시간이 아닙니다"가 보입니다. `409 COUPON_NOT_STARTED`
   4. 발급 기간이 끝났으면 "발급 기간이 끝난 쿠폰입니다"가 보입니다. `409 COUPON_ISSUE_ENDED`
   5. 이미 받은 회원이면 "이미 받은 쿠폰입니다"가 보입니다. `409 COUPON_ALREADY_ISSUED` (같은 회원 중복 요청)
   6. 한정 수량을 다 썼으면 "쿠폰이 소진되었습니다"가 보입니다. `409 COUPON_SOLD_OUT` (초과 발급)
3. 모두 통과하면 회원 쿠폰이 생기고 "쿠폰을 받았습니다"가 보입니다. `201`
4. 저장에 실패하면 차감한 수량을 되돌리고 "잠시 후 다시 시도해 주세요"가 보입니다. `503 COUPON_RETRY` (발급 수 불일치)

경계 상황:

- 마지막 수량에 여러 명이 동시에 누르면 남은 수량만큼만 받고, 나머지는 소진 응답을 받습니다. (초과 발급)
- 같은 회원이 짧은 시간에 여러 번 눌러도 한 장만 받습니다. 두 번째 요청부터는 이미 받음 응답을 받고 서버 에러는 0건입니다. (같은 회원 중복 요청)
- 소진 응답을 받은 회원이 다시 누르면 보통 다시 소진 응답을 받습니다. 다른 회원의 저장이 실패해서 자리가 다시 나면 받을 수 있습니다.
- 응답을 받기 전에 연결이 끊기면 회원 쿠폰이 생겼는지 알 수 없습니다. 다시 누르면 이미 받음 응답이 오거나 새로 받는데, 어느 쪽이든 한 장입니다.
- Redis에는 없는데 DB에는 이미 회원 쿠폰이 있으면 Redis 기록이 어긋난 경우입니다. 회원이 실제로 쿠폰을 받은 상태라서 이미 받음 응답을 줍니다. 자세한 처리는 [Flow 실패 처리](flows.md#실패-시-처리)에 있습니다. (발급 수 불일치)
- 확인에 쓰는 쿠폰 정보를 1초 캐시해서, 발급 중단 직후 1초 동안 들어온 요청은 발급될 수 있습니다 (가정).

요청이 1분 동안 몰려도 위 응답은 목표 시간 안에 와야 합니다. (발급 지연·에러)

## 시나리오 3. 회원 쿠폰 목록 보기

사전 조건: 로그인한 회원입니다.

1. 회원이 자기 회원 쿠폰 목록 화면을 엽니다.
2. 받은 회원 쿠폰이 최근에 받은 순서로 보입니다.
3. 회원 쿠폰마다 상태가 보이고, 상태는 저장된 값과 사용 기한으로 계산합니다.
   - 사용 가능: `ISSUED`이고 지금이 사용 기한 전입니다.
   - 사용함: `USED`입니다. 사용 기한이 지나도 사용함으로 보입니다.
   - 만료: `ISSUED`이고 지금이 사용 기한 이후입니다.
4. 사용 가능, 사용함, 만료 상태로 거를 수 있습니다.
5. 발급 중단된 쿠폰의 회원 쿠폰도 그대로 보이고 쓸 수 있습니다.
6. 주문을 취소해서 돌려받은 회원 쿠폰은 다시 사용 가능으로 보이고, 사용 기한이 지났으면 만료로 보입니다. (주문을 만들 때)

- 목록은 회원 쿠폰과 쿠폰을 JOIN해서 만듭니다. 쿠폰 삭제는 발급 시작 전에만 하므로 삭제된 쿠폰에 딸린 회원 쿠폰이 없고, JOIN에서 회원 쿠폰이 조용히 사라지는 일도 없습니다 ([삭제 정책](../../reference/erd.md#삭제-정책)).

## 시나리오 4. (시스템) 발급 준비와 Redis 복구

관련 Risk: 발급 수 불일치, Redis 재시작

발급 결정에 쓰는 Redis 키를 DB 기준으로 채우는 일이고, 회원이 직접 하지 않습니다.

#### 발급 준비

1. 스케줄러가 발급 시작 5분 전에 돕니다 (가정).
2. `ACTIVE`이고 삭제되지 않았으며 발급 시작이 5분 안에 오는 쿠폰을 찾습니다.
3. 쿠폰마다 DB 기준으로 Redis 키를 새로 만듭니다.
   - `coupon:{id}:members` = 그 쿠폰의 회원 쿠폰 `member_id` 전체
   - `coupon:{id}:count` = 그 쿠폰의 회원 쿠폰 수
   - 수는 [집계 규칙](../../reference/erd.md#집계-규칙)대로 `member_coupon`만 세고, 다른 테이블과 JOIN하지 않습니다.
4. 발급 시작 전이라 보통 둘 다 비어 있지만, 복구와 같은 코드를 쓰려고 같은 방법으로 채웁니다.

#### Redis 복구

Redis가 재시작됐거나 수량이 어긋났을 때 합니다.

1. 운영자가 쿠폰을 발급 중단(`STOPPED`)합니다. 관리자 기능이 없어서 SQL로 바꿉니다 (가정).
2. 쿠폰 정보 캐시가 만료되도록 1초 이상 기다립니다.
3. 발급 준비와 같은 방법으로 Redis 키를 다시 만듭니다.
4. 쿠폰을 다시 `ACTIVE`로 바꿉니다.

- 다시 채우는 사이에 발급이 끼어들면 그 발급이 복구 값에서 빠지므로, 복구하는 동안에는 발급을 멈춥니다.
- Redis 재시작을 자동으로 알아채는 장치는 아직 없습니다. 재시작 뒤 복구 전에 발급이 열려 있으면 발급 수가 0부터 다시 시작해 초과 발급이 생깁니다 (Redis 재시작).

## 허용하는 지연·불일치

- 행사 쿠폰 목록의 남은 수량은 몇 초 늦거나 실제보다 잠깐 적게 보일 수 있습니다.
- 확인 1~4번에 쓰는 쿠폰 정보는 서버 메모리에 1초 캐시하므로, 발급 중단이 최대 1초 늦게 반영됩니다 (가정).
- 회원 쿠폰 수는 어떤 순간에도 한정 수량을 넘으면 안 됩니다.
- 발급받은 회원 쿠폰은 1초 안에 회원 쿠폰 목록에 보여야 합니다 (목표, 미검증).
- 서버가 발급 도중 죽으면 그 자리만큼 잠깐 덜 발급될 수 있고, Redis 복구를 하면 다시 채워집니다.

## 공개 서비스 (다른 모듈이 부르는 것)

주문 모듈이 쿠폰 모듈의 `index.ts`가 공개한 서비스를 함수로 부릅니다 ([모듈 사이의 규칙](../../reference/conventions.md#모듈-사이의-규칙)).
모든 메서드는 호출한 쪽의 트랜잭션에 참여합니다 (`@nestjs-cls/transactional`).

| 메서드 | 입력 | 하는 일 | 실패 |
|---|---|---|---|
| `getUsableCoupons(memberId, now)` | 회원 ID, 지금 시각 | `ISSUED`이고 사용 기한이 남은 회원 쿠폰과 쿠폰 정보(적용 범위, 할인, 최소 주문 금액, 대상 상품·브랜드)를 돌려줍니다. 고르는 판단은 주문 모듈이 합니다 | |
| `useCoupon(memberId, memberCouponId)` | 회원 ID, 회원 쿠폰 ID | `UPDATE member_coupon SET status = 'USED', used_at = now() WHERE id = ? AND member_id = ? AND status = 'ISSUED'`. 바뀐 행이 0개면 실패 | 쓸 수 없는 쿠폰 (주문 모듈이 `409 ORDER_COUPON_UNAVAILABLE`로 응답) |
| `restoreCoupon(memberCouponId)` | 회원 쿠폰 ID | `UPDATE member_coupon SET status = 'ISSUED', used_at = NULL WHERE id = ? AND status = 'USED'`. 사용 기한이 지났어도 되돌립니다 | |

- 주문 모듈은 회원 쿠폰 ID 오름차순으로 한 장씩 부릅니다 ([주문 Flow](../order/flows.md)).
