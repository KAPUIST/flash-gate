# 쿠폰 발급은 Redis가 결정하고, DB는 기록만 한다

- 상태: 채택
- 날짜: 2026-11-06
- 관련 Risk: 초과 발급, 발급 수 불일치, 발급 지연·에러, Redis 재시작

## 문제

행사 시작 직후 10만 명이 1만 장을 두고 쿠폰을 받으려 해서, 요청의 90%는 결국 소진 응답입니다 ([가정](../reference/problem.md#가정-트래픽)).
DB만으로 수량을 지키면 모든 요청이 쿠폰 행 하나의 잠금을 기다립니다. 잠금을 2ms 잡는다고 하면 그 행은 초당 약 500건이 한계입니다 (가정, 미검증).

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. DB 조건부 UPDATE (`issued_quantity < total_quantity`) + 같은 트랜잭션에서 INSERT. A를 쓰려면 `issued_quantity` 컬럼이 필요합니다 | 기준이 한 곳이라 어긋날 일이 없고, 초과 발급·부분 실패를 트랜잭션이 막습니다 | 소진될 9만 건까지 모두 쿠폰 행 잠금을 기다립니다 |
| B. Redis는 문지기, DB 카운터가 기준 | DB CHECK가 초과 발급을 끝까지 막습니다 | 카운터가 두 곳이라 어긋나면 덜 발급됩니다. 성공 요청은 여전히 쿠폰 행 잠금을 기다립니다 |
| C. Redis가 결정, DB는 회원 쿠폰 행만 기록, 복구는 DB 기준 | 소진 요청이 DB에 가지 않고 쿠폰 행 잠금도 없습니다. 카운터는 Redis 한 곳입니다 | DB가 초과 발급을 스스로 막지 않습니다. Redis가 재시작되면 DB 기준으로 복구해야 합니다 |

## 결정

C를 씁니다.

1. `SADD coupon:{id}:members {memberId}`가 0을 돌려주면 이미 받은 회원으로 보고 거절합니다 (409).
2. `INCR coupon:{id}:count`의 결과가 한정 수량을 넘으면 `SREM`과 `DECR`로 되돌리고 소진으로 거절합니다 (409). `DECR`을 하지 않으면 발급 수가 한정 수량을 넘어 쌓여서, 저장 실패로 되돌린 자리가 다시 열리지 않습니다.
3. DB에 회원 쿠폰을 INSERT하고, `UNIQUE(member_id, coupon_id)`가 중복을 한 번 더 막습니다.
4. 3이 실패하면 실패 종류에 따라 처리합니다 ([쿠폰 Flow 실패 시 처리](../features/coupon/flows.md#실패-시-처리)).
   - UNIQUE 위반이면 회원이 실제로 이미 받은 것이므로 `DECR`만 하고 회원은 SET에 남긴 채 409로 응답합니다.
   - 실패한 것이 확실하면 `SREM`과 `DECR`로 되돌리고 503으로 응답합니다.
   - 타임아웃처럼 결과를 모르면 회원 쿠폰을 다시 읽어서, 행이 있으면 201로 응답합니다. 행이 없거나 읽기도 실패하면 SREM만 하고 DECR은 하지 않은 채 503으로 응답합니다. DECR을 하면 늦게 커밋된 INSERT 때문에 Redis 발급 수가 DB보다 작아져 초과 발급이 생기므로, 남는 어긋남을 덜 발급 쪽으로만 둡니다.

DB 카운터(`coupon.issued_quantity`)는 두지 않습니다. 발급 수는 회원 쿠폰 행 수입니다 ([집계 규칙](../reference/erd.md#집계-규칙)).

## 이유

- Redis를 쓰는 목적은 DB 부담을 줄이는 데 있습니다. 가장 큰 이득은 소진될 요청을 DB까지 보내지 않는 것이고, B와 C 모두 이 이득을 얻습니다. C는 여기에 더해 성공 요청도 쿠폰 행 잠금을 기다리지 않습니다.
- 어긋남은 같은 숫자를 두 곳에서 따로 셀 때 생깁니다. C는 숫자를 Redis 한 곳에서만 세고, Redis 상태는 언제든 DB 행으로 다시 만들 수 있습니다.
- 올리브영 등 국내 선착순 쿠폰 사례도 Redis가 판정하고 DB 기록은 따로 하는 구조입니다 ([올리브영](https://oliveyoung.tech/2025-12-15/fcfs-coupon/), [여기어때](https://techblog.gccompany.co.kr/redis-kafka%EB%A5%BC-%ED%99%9C%EC%9A%A9%ED%95%9C-%EC%84%A0%EC%B0%A9%EC%88%9C-%EC%BF%A0%ED%8F%B0-%EC%9D%B4%EB%B2%A4%ED%8A%B8-%EA%B0%9C%EB%B0%9C%EA%B8%B0-feat-%EB%84%A4%EA%B3%A0%EC%99%95-ec6682e39731)).
- 아직 실험으로 검증하지 않은 판단입니다. [실험](../experiments/)에서 [쿠폰 Flow](../features/coupon/flows.md)의 Before 구현(`CountThenInsertIssuance`, `PessimisticLockIssuance`)과 `RedisFirstIssuance`를 같은 시나리오로 재서 이 ADR에 링크합니다.

## 감수하는 것

- DB가 초과 발급을 막지 않아서, 초과 발급 0은 INCR의 성질과 부하 테스트 결과(회원 쿠폰 수 ≤ 한정 수량)로 증명합니다.
- Lua 없이 명령 두 개(SADD, INCR)를 따로 보내서, 그 사이나 DB 저장 전에 서버가 죽으면 Redis와 DB가 어긋납니다. 어긋남은 복구 작업으로 메우고, Lua로 묶는 개선은 실험으로 비교합니다. 올리브영은 처리 성능이 약 21% 떨어진다는 이유로 Lua를 기각했습니다.
- Redis가 재시작되면 카운터가 0부터 시작해서, 발급을 다시 열기 전에 DB 기준으로 복구하지 않으면 초과 발급됩니다 (Redis 재시작).
- 이 결정은 실험 결과(특히 발급 지연·에러의 p99)를 보고 다시 검토합니다.
