# 모듈러 모놀리스로 만들고, 포트는 발급 전략 하나만 둔다

- 상태: 채택. 포트를 하나만 둔다는 부분은 [모듈 사이 반응은 이벤트로](0003-module-reactions-through-events.md)이 고칩니다 (이벤트 발행 포트 추가)
- 날짜: 2026-11-06
- 관련 Risk: 없음 (구조 결정)

## 문제

클린·헥사고날 구조를 좋아하지만, 정석대로 모든 저장소에 포트·어댑터·매퍼를 두면 파일과 매핑 코드가 크게 늘어납니다.
이 프로젝트는 Redis 방식과 DB 방식처럼 같은 기능의 구현을 갈아 끼우며 실험해야 합니다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 계층형 (controllers/, services/, repositories/) | 단순함 | 기능 하나가 폴더 전체에 흩어지고, 모듈 경계가 없습니다 |
| B. 정석 헥사고날 전체 | 모든 외부 의존이 포트 뒤에 있습니다 | 포트·DTO·매퍼가 저장소마다 생기고, 구현이 하나뿐인 포트가 대부분입니다 |
| C. 모듈러 모놀리스 + 구현을 비교하는 곳에만 포트 | 기능 폴더 하나에 맥락이 모이고, 헥사고날의 의존성 규칙(도메인은 바깥을 모른다)은 지킵니다 | 경계를 도구로 강제하지 않으면 무너집니다 |

## 결정

C를 씁니다.

- 기능마다 Nest 모듈 하나를 두고, 모듈 안은 유스케이스 폴더로 나눕니다 ([폴더 구조](../reference/conventions.md#아키텍처)).
- 다른 모듈은 `index.ts`가 공개한 서비스만 함수로 호출하고, 다른 모듈의 테이블은 직접 쓰지 않습니다.
- 포트는 지금 `IssuanceStrategy.issue()` 하나이고, 저장소 단위가 아니라 전략 단위로 자릅니다. Redis 방식과 DB 방식은 트랜잭션 모양이 달라서, 저장소 단위로 자르면 트랜잭션 경계가 서비스로 새어 나옵니다.
- 경계는 dependency-cruiser로 CI에서 검사합니다.

## 이유

#### 모듈러 모놀리스로 만드는 이유

- 배포 단위는 하나로 두고, 안쪽은 기능 모듈별로 나눕니다. 정의는 [NestJS 책의 모듈러 모놀리스 장](https://wikidocs.net/346034)을 따릅니다.
- 서비스를 나누면 네트워크 지연, 분산 트랜잭션, 운영 부담이 생깁니다. 이 프로젝트가 재려는 것은 서버 한 대 안의 동시성 문제라서, 그 비용을 먼저 질 이유가 없습니다.
- 주문은 재고·쿠폰·포인트를 한 트랜잭션에서 바꿔야 합니다. 모놀리스라서 DB 트랜잭션 하나로 묶을 수 있습니다.
- Nest 모듈의 `exports`에는 서비스만 넣고 Repository는 넣지 않아서, 다른 모듈이 테이블을 직접 쓰지 못합니다.
- 기능 하나를 고칠 때 볼 파일이 기능 폴더 하나에 모이고, 모듈 경계는 검사 도구가 지킵니다.

#### 포트를 발급 전략 하나만 두는 이유

- 헥사고날에 대한 비판은 의존성 규칙이 아니라 기계적인 적용(구현이 하나뿐인 인터페이스, 계층마다 DTO와 매퍼)을 겨눕니다.
- [카카오페이 홈 서버](https://tech.kakaopay.com/post/home-hexagonal-architecture/)는 2023년에 헥사고날을 도입했다가 2025년에 걷어냈습니다. out 포트가 40개를 넘었고, 걷어낸 뒤 코드가 8,000줄 넘게 줄었습니다. 글쓴이가 든 적합 조건은 "도메인이 명확하다, 핵심 로직이 외부 의존보다 많다, 코어를 쓰는 진입점이 둘 이상이다"입니다. 이 프로젝트는 지금 세 조건을 모두 만족하지 않습니다.

## 감수하는 것

- Nest 모듈은 파일 import를 막지 못해서, 모듈 경계는 Nest 모듈만으로 지켜지지 않습니다. 그래서 dependency-cruiser 규칙이 꼭 있어야 합니다.
- 결제를 붙이면서 비동기 워커가 발급이나 주문 유스케이스를 함께 부르게 되면 인바운드 포트를 다시 검토합니다.
